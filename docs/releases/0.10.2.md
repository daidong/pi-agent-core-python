# 0.10.2：应用直接执行工具，来源记录可选输出

本版本新增 `Agent.execute_tools()`，让应用直接执行已注册工具，不必先请求模型决定调用。两种入口共用工具执行与清理路径；旧工具事件默认保持原有字段集合。

## 新增能力

- `ToolInvocation(name, arguments)` 与 `await agent.execute_tools(invocations, source=None)`：独立工具批次，无模型请求，共用参数准备、schema 验证、执行前后钩子、并发限制、预算、超时和取消清理。
- 应用结果通过内置 `application_tool_batch` 自定义消息记录；不伪造 assistant 工具调用，不生成没有对应调用的 `ToolResultMessage`。
- `ToolContext.origin/source` 与 `ToolOutcome.origin/source` 只读属性，用于区分模型选择与应用指定的调用。来源标签是诊断信息，不是认证身份。
- `Agent(include_tool_origin=True)` 可将来源加入工具事件；默认关闭，两种入口都遵守该选项。
- `require_features(["application-tool-batches-v1"])` 可检查是否支持此合同。
- 无网络能力包组合示例，演示同一个工具的两种调用方式，以及“运行 completed，但领域验证失败”。没有新增包加载器或领域判断引擎。

## 兼容性与接入注意事项

### 沿用旧接口

原有 `prompt/continue_run` 保持整数轮次 ID，不自动生成应用批次消息。工具事件默认不新增 `origin/source`；`ToolContext` 和 `ToolOutcome` 的 dataclass 字段及 `dataclasses.asdict()` 输出结构保持不变。来源信息需要显式读取属性，或从批次历史、开启来源输出后的事件中保存。

### 采用新接口或读取新记录

1. 应用批次没有模型轮次，其事件的 `turn_id=None`。监听器、数据库字段和事件解析器需要允许这种情况；对 None 做整数运算会出错，关键订阅者失败可能使运行失败。
2. 没有自定义消息转换器时，core 自动转换内置批次消息。已有 `transform_context/convert_to_llm` 应保留该消息供 core 转换，或自行明确转换。拒绝未知类型可能导致后续模型运行失败；过滤全部自定义消息可能静默丢掉工具反馈。
3. `application_tool_batch` 是内置消息类型名；已有同名自定义类型的应用应检查其数据与转换规则。
4. 每批预算只约束当前运行；跨多次运行的任务总预算和领域验收由应用负责。`completed` 不代表领域验证通过。

本版本没有更改默认资源上限、现有插件加载机制或上游参照基线。上述接入边界已经说明，并经项目负责人确认后安排发布；这不等于已验证所有实际上层应用。

## 验证

本地 macOS ARM64 / Python 3.14：全量测试 798 通过、2 跳过；C28、C29 与兼容性定向测试 47 通过；25 组实际上游核心差分通过。Ruff、格式与 mypy 检查通过。两项跳过只适用于不支持 `meta` 的旧版 MCP SDK，不计入通过数。

0.10.2 的 wheel 与源码包通过 `twine check --strict`。wheel 已在仓库外的独立 Python 3.11 环境中安装，版本一致性、组合示例和 43 项应用批次及兼容性测试通过。

发布由 `v0.10.2` 标签触发，CI 验证和构建成功后才上传 PyPI。没有以模拟示例宣称真实模型、HPC 或领域效果已经验证。

## 使用与文档

```python
from pi_python import ToolInvocation

result = await agent.execute_tools(
    [ToolInvocation("check_sample", {"value": -1})], source="sample-checks@1"
)
# 根据 result.tool_outcomes 验收，而不是仅检查 result.status。
await agent.prompt("解释应用检查的结果。")
```
