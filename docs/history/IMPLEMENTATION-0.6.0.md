# 实施与验证结果（0.6.0 存档）

这一轮对照固定的上游 Pi `v1.0.0`，检查了"模型出错"和"运行被取消"两条路径。我们发现本库有三处做法与上游不同，却没有写进文档；另外，取消一个正在运行的工具会让整个 Agent 再也不能用。0.6 把这些都改成上游的做法，并把所有运行上限交给应用设置。依赖旧的取消行为或默认上限的应用会看到不同结果，需要按[迁移表](../API.md#06-迁移)检查。

## 要解决的问题

Pi 的一条基本做法是"出错也是数据"：模型出错或被取消时，这次回答本身，连同已经生成的内容和错误原文，照常写进历史；这一轮也照常收尾，调用 `finish_turn`、发出 `turn_end`。上层应用靠读这条回答决定下一步，例如发现"上下文超长"后先压缩历史再重试。

例子：模型流式输出到一半，供应商返回"prompt is too long"。

- 0.5 在历史里写一条空回答，供应商和模型名都是 `mock`，已经生成的文字丢了。应用无从判断失败原因。
- 0.6 与 Pi 相同：历史里是供应商给的那条失败回答，带着已生成的文字、真实的供应商和模型名、用量和错误原文。

取消也有同样的问题。0.5 中，用户中途取消一个读文件的工具后，这次调用被标成"结果未知"，之后 `prompt` 和 `reset` 都被拒绝，只能新建 Agent。这项保护原本是为了防止重复提交集群作业，却对所有工具一视同仁。Pi 的做法是：把取消信号交给工具，工具结束后它的结果作为普通错误结果交还模型，Agent 继续可用。

## 改了什么

| 情况 | 0.5 | 0.6（与上游相同） |
|---|---|---|
| 模型流到一半出错 | 空回答，内容和身份丢失 | 记录供应商的失败回答，然后照常收尾 |
| 模型流到一半被取消 | 不调用 `finish_turn`，不发 `turn_end`，不留回答 | 已生成的部分记成一条"已取消"回答，然后照常收尾 |
| 执行前钩子 `before_tool_call` 抛异常 | 整个运行失败 | 只有这次调用得到错误结果，模型继续 |
| 工具运行中被取消或超时 | 标成结果未知，实例被锁 | 普通错误结果，实例可继续使用 |
| 默认上限 | 32 次模型请求、128 次工具调用、并发 4 | 都不设，由应用设置 |

只有工具主动抛出 `ToolOutcomeUnknownError` 时，才会停止运行并锁定实例。例如作业已经提交，但在拿到作业号之前连接断了。这项保护是本库在 Pi 之外特意保留的。

Python 边界上还保留几处与上游不同的取消行为。例如：工具在取消后 1 秒内没有停下，运行会立即停止，这个实例不能再用；上游会一直等工具结束。完整清单见[验收映射的修订记录](../../compat/COVERAGE.md#06-修订失败与取消对齐-pi)。

## 验证结果

| 要回答的问题 | 证据 |
|---|---|
| 新行为是否与上游一致？ | 新增 4 组差分：模型中途出错、流中取消、工具运行中取消、执行前钩子抛错。Python 结果与固定上游实际运行的结果逐项相同。0.5 在这 4 种情况下的行为已用复现脚本确认与上游不同 |
| 原有行为是否改变？ | 原有 21 组核心差分、34 组 Provider 差分、2 组 WebSocket 差分仍全部相同 |
| 测试是否通过？ | Python 测试 239 项通过；上游相关测试 147 项通过；ruff 与 mypy 无问题 |
| 能否在 Linux 安装？ | Python 3.11、3.12、3.13 容器内断网安装 0.6.0 wheel，示例和全部测试通过。3.12 镜像为 x86_64，在 arm64 主机上模拟运行，与 0.5 的记录相同 |

真实账号联调没有在 0.6 重跑。Provider 的网络代码没有改，但 Agent 处理供应商错误和取消的方式改了。这些改动用本地脚本流和上游差分验证，没有经过真实服务。

仍未实现：约束采样、后台任务轮询、上下文压缩与会话保存等应用层功能。Pi 也把压缩和会话保存放在应用层（coding-agent）和 pi-durable，不在核心里。
